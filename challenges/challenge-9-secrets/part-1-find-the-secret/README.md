# Challenge 9, part 1: find the secret

**Time:** about 30 minutes. **Download:** the `random` and `local` providers (about 40 MB) the first time `init` runs. No Docker objects are created. Every secret in this challenge is fake or random: no real credential is ever used. **Safety rules:** [SAFETY.md](../../../SAFETY.md)

## The problem

Your config marks the database password `sensitive = true`. The plan says `(sensitive value)`. The reviewer is happy. Then someone zips the project folder to ask for help, or a CI job uploads the working directory as an artifact, and the password goes with it. Where, exactly?

You will answer that question here, one place at a time, before you look.

## The idea

A **secret** is a value that must not leak: a password, a token, a key. Terraform handles secrets in two quite different ways, and mixing them up is the usual mistake:

| What | What it does |
|---|---|
| `sensitive = true` on a variable or output | Hides the value in the text Terraform prints to your screen. That is all. The value is still stored. |
| State (`terraform.tfstate`) | A plain JSON file. Every value Terraform manages is in it, including secrets and including values marked sensitive. |
| A saved plan (`-out=tfplan`) | Also holds the values, in a binary file that `terraform show -json` turns into plain JSON. |
| `terraform show -json` and `terraform output -json` | Print the real values. The word `sensitive` appears in the JSON as a flag, and the value is next to it. |

So `sensitive` is about **screens**. It is not about **files**. Part 2 shows how to keep a secret out of the files; this part makes you see them.

The config has two secrets. `db_password` is passed in by the caller (the run uses the fake value `fake-db-password-not-real`). `random_password.api` is generated by Terraform, so you could not guess it. The run looks for the fake value in nine places and, for state and `output -json`, also checks the generated one without printing it.

## Steps

| # | Command | What happens |
|---|---|---|
| 1 | Open `predictions.json` | Nine places. For each, `true` means "the fake secret shows up there in plain text". The starter says `false` everywhere. |
| 2 | Think first. Change the values you believe are wrong | Do not run anything yet. For each place ask: is this text on a screen, or a file? |
| 3 | `node challenges/challenge-9-secrets/part-1-find-the-secret/run.mjs` | Applies the config, looks in every place, prints one step per place and compares with your predictions. |
| 4 | Read each step, fix the wrong predictions, run step 3 again | The run takes about a minute. |
| 5 | `node --test challenges/challenge-9-secrets/part-1-find-the-secret/test.mjs` | One test per place. It fails until the prediction is right. |
| 6 | `node toolkit/show-facts.mjs c9.p1` | Shows the saved facts. |

`reference/predictions.json` holds the right answers. `TFC_REFERENCE=1 node challenges/challenge-9-secrets/part-1-find-the-secret/run.mjs` runs with them.

## What you should see

The recorded run, in [results.md](results.md), finds the fake secret in plain text here:

| Place | Found | Why |
|---|---|---|
| `terraform.tfstate` | yes | State holds every value. |
| `terraform.tfstate.backup` | yes | Each state write keeps the previous state. |
| `terraform show -json` | yes | It prints the state as JSON. |
| `terraform output -json` | yes | It prints sensitive outputs in full. |
| `terraform show -json <planfile>` | yes | A saved plan holds the values too. |
| `app.conf` | yes | The config asked for a file with the secret in it. |
| `terraform output` (no flags) | no | It prints `<sensitive>`. |
| `terraform plan` (the text) | no | It prints `(sensitive value)`. |
| `TF_LOG=TRACE` | no | In this run the most detailed log, over two thousand lines, did not print it. |

The last row is a fact about this run, not a promise. A provider that logs its requests, a script that runs `echo $TF_VAR_db_password`, or a CI system that prints environment variables would put the secret in a log. Part 3 builds a scanner for that.

The generated password is in state and in `output -json` too (`c9.p1.generated_in_state` and `c9.p1.generated_in_output_json`).

## Where each number comes from

| Fact | Where it comes from |
|---|---|
| `c9.p1.init_ok`, `c9.p1.apply_ok` | Exit codes of `terraform init` and `terraform apply`. |
| `c9.p1.found_<place>` | True when the fake value `fake-db-password-not-real` appears in that place. Places: `tfstate`, `tfstate_backup`, `show_json_state`, `output_human`, `output_json`, `plan_text`, `show_json_plan`, `app_conf`, `trace_log`. |
| `c9.p1.generated_in_state`, `c9.p1.generated_in_output_json` | True when the random password read from state also appears there. |

| `c9.p1.matches_prediction_count` | How many of your nine predictions equal what was found. 9 is the goal. |

## What is different on your platform

- **Linux and WSL2, Docker Desktop, Codespace:** the same. The toolkit runs `hashicorp/terraform:1.17.1` unless a local Terraform 1.17 or newer is on your PATH. The generated password differs on every run; the fake value does not.
- **Docker socket:** not needed in this part.
- **OpenTofu:** not run in this part. Challenge 13 compares the two tools.

## Stuck?

- The run says `WRONG` for a place: read that place's step. The line `fake secret in plain text` is the answer, and the lines under it are the evidence.
- You are sure `terraform output` hides the value but your prediction says otherwise: run `terraform output` yourself in `work/` and look.
- `predictions.json` must stay valid JSON, with the exact place names as keys.
- The test still fails after you fixed the predictions: run step 3 first. The test reads the numbers of the last run.
