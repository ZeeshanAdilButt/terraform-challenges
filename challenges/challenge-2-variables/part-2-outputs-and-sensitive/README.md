# Challenge 2, part 2: outputs and sensitive values

**Time:** about 45 minutes. **Download:** the `random` provider (a few MB), once. **Safety rules:** [SAFETY.md](../../../SAFETY.md)

## The problem

A teammate marks a password `sensitive = true`, sees `<sensitive>` in the pipeline log, and tells the security channel: "it is hidden". Two days later an audit finds that password in the state file, in the output of one `terraform output` command, and in the JSON a dashboard reads. Nothing was hacked. Everything worked as designed. The word "sensitive" meant something smaller than the teammate thought.

In this part you measure what `sensitive` does and what it does not do. Real secrets never appear: the password is generated by Terraform and thrown away, and the token is made up (`tfc-demo-token-not-real`).

## The idea

An **output** is a value a configuration reports after an apply. People read it, and other tools can read it too (`terraform output -json`).

`sensitive = true` on a variable, an output, or a provider attribute does one job: **it makes Terraform print `<sensitive>` or `(sensitive value)` instead of the value in its normal screen output.** It exists to stop accidents, such as a secret in a CI log.

It does not encrypt anything, and it does not stop anyone who can run a command or read a file.

Three more facts you will see with your own eyes:

1. **Sensitivity spreads and must be written down.** A value built from a sensitive one is sensitive too. If an output uses such a value and you do not write `sensitive = true`, Terraform refuses to plan: `Error: Output refers to sensitive values`. It makes you confirm in writing.
2. **Some commands print the value on purpose.** `terraform output NAME`, `terraform output -raw NAME` and `terraform output -json` print the real value, because a script that asks for the password by name wants the password.
3. **State keeps everything.** Every attribute of every resource is written to the state file in clear text, sensitive or not. And a mark can be lost along the way: the resource `terraform_data` copies its `input` to an `output` attribute, and the copy is not marked.

(Challenge 9 shows how to keep secrets out of state with ephemeral values and write-only attributes. Here, you only learn what the plain mark does.)

## What you should see

In the recorded reference run:

- The unmarked output stops the plan with `Error: Output refers to sensitive values`, a pointer to the output, and the fix: `sensitive = true`.
- The apply prints `(sensitive value)` in `Changes to Outputs` and `<sensitive>` in `Outputs`.
- `terraform output` lists `db_password = <sensitive>`; `terraform output db_password`, `-raw` and `-json` print the generated password.
- `terraform show` hides the password but prints the made-up token in plain text in the `output` attribute of `terraform_data.service`.
- `terraform.tfstate` holds both, in clear text.

## Stuck?

- `Error: Output refers to sensitive values` after your edit: the message names the line of the output that is still missing `sensitive = true`. There are two outputs to fix.
- The test says only two outputs may be sensitive: `service_name` is not a secret; leave it plain.
- Do not put a real password or token anywhere in these files. A state file keeps what you give it, in clear text.
